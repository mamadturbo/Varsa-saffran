# راه‌اندازی و عملیات بک‌اند ورسا

برای احراز هویت، MFA، نقش دیتابیس، هدرها و فعال‌سازی production،
[راهنمای امنیت](security/deployment.md) مرجع جدید است. رمز مشترک مدیر معتبر نیست.
فایل‌های شکست‌خورده اکنون قبل از ارسال S3 سهمیه رزرو می‌کنند؛ نگاشت بدون object
باید توسط اپراتور reconcile شود؛ این تفاوت، توضیح قدیمی «نگاشت فقط پس از PUT» را جایگزین می‌کند.

این راهنما مرجع فعلی است. گزارش‌های STAGE و فایل‌های `docs/history/` وضعیت
تاریخی‌اند. هیچ migration یا استقراری روی محیط عملیاتی در این کار اجرا نشده است.

## اجرای محلی

برای پیش‌نمایش محلی بدون تنظیم سرویس خارجی، از ریشهٔ پروژه اجرا کنید:

```sh
pnpm dev
```

این فرمان بک‌اند پورت ۵۰۰۰ و فروشگاه پورت ۵۱۷۳ را با هم اجرا می‌کند.
PostgreSQL و فضای فایل محلی فقط روی loopback باز می‌شوند؛ داده‌ها، فایل‌ها و
کلیدهای توسعه در `.local/development/` بین اجراها حفظ می‌شوند. این دیتابیس
مستقل است و داده‌های پیش‌نمایش‌های قدیمی را تغییر نمی‌دهد. نخستین اجرا
migrationهای موجود و کاتالوگ اولیه را روی همین دیتابیس جدید اعمال می‌کند.
کد ورود آزمایشی داخل فرم نمایش داده می‌شود و پیامک واقعی ارسال نمی‌شود.
این فرمان `.env` استقرار را نمی‌خواند و برای production مجاز نیست.
برای اجرای فقط بک‌اند محلی: `pnpm --filter @workspace/api-server dev:local`.
اجرای فقط فرانت‌اند با بک‌اند تنظیم‌شدهٔ خودتان: `pnpm dev:web`.
اگر سرویس قطع شود، به‌جای پیام گمراه‌کنندهٔ «صفحه را تازه کنید»، خطای اتصال
به سرور نمایش داده می‌شود.

Node.js 24، pnpm مطابق `packageManager`، PostgreSQL با UTF8 و یک bucket خصوصی
S3-compatible لازم است. سرویس PostgreSQL آزمایش با بستهٔ `embedded-postgres`
خودکار ایجاد می‌شود؛ این بسته وابستگی توسعه است و دیتابیس عملیاتی نیست.

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm --filter @workspace/api-server test
pnpm --filter @workspace/api-server verify:deployment
```

فرمان آخر PostgreSQL واقعی و S3rver محلی ایجاد می‌کند، CLI مهاجرت را اجرا می‌کند،
API ساخته‌شده را راه می‌اندازد و build سخت‌گیرانهٔ متادیتا می‌گیرد. داده، دامنه
و مقالهٔ آن آزمایشی‌اند. سرویس‌ها و پوشه‌های موقت در پایان پاک می‌شوند.
روی Windows تنها build script بستهٔ PostgreSQL مربوط به این معماری مجاز شده است؛
برای معماری دیگر همان بستهٔ رسمی platform را در `allowBuilds` بررسی کنید.

برای اجرای توسعهٔ عادی، نمونهٔ `artifacts/api-server/.env.example` را به `.env`
همان پوشه کپی و تنظیم کنید؛ `DATABASE_URL` باید دیتابیس توسعه باشد. سپس:

```sh
pnpm dev:api
pnpm dev:web
# در فرایند سوم، پس از build:
pnpm --filter @workspace/api-server worker
```

بک‌اند تنظیمات فرانت را خودکار بارگذاری نمی‌کند. فایل نمونهٔ فرانت فقط تنظیمات
عمومی دارد و کلید Supabase لازم ندارد. تمام درخواست‌های مرورگر، شامل contact و
متادیتای مقاله، از `/api` می‌گذرند. تنظیمات Supabase در سرور صرفاً برای واردکردن
مقالات قدیمی است و پس از انتقال قابل حذف است.

## مهاجرت روی نسخهٔ ایزوله

نخست backup و copy فایل‌ها را بازیابی کنید. نوشتن برنامهٔ قدیمی در زمان cutover
باید متوقف باشد. با نقش مالک migration و اتصال **صریح** اجرا کنید؛ CLI هیچ `.env`
را ضمنی بارگذاری نمی‌کند. نمونهٔ PowerShell:

```powershell
$env:DATABASE_URL = 'postgresql://MIGRATOR:PASSWORD@127.0.0.1:5432/varsa_staging'
$env:MIGRATION_TARGET_ACK = 'isolated-or-approved'
# تنظیم S3 و در صورت نیاز SUPABASE_URL / SUPABASE_ANON_KEY در محیط سرور
pnpm --filter @workspace/api-server migrate:commerce --copy-files --import-articles
```

برای دیتابیس واقعاً خالی، `--seed-empty` را اضافه کنید تا کاتالوگ دوازده‌تایی
به‌طور صریح ایجاد شود. برنامهٔ زمان اجرا هیچ seed یا fallback قیمت ندارد.
وجود سند `store_management/main` بر seed مقدم است. کاتالوگ نیمه‌منتقل‌شده باعث
توقف و rollback تراکنش backfill می‌شود.

CLI یک قفل اختصاصی migration می‌گیرد، SQLها را با checksum در `schema_migrations`
ثبت می‌کند و داده را تراکنشی منتقل می‌کند. تغییر فایل SQL قبلاً اعمال‌شده خطاست؛
برای تغییرات بعدی migration جدید بسازید. migrationها افزایشی‌اند. از
`drizzle-kit push` و `push-force` برای cutover استفاده نکنید.

خروجی JSON شامل تعداد محصول، سفارش، جمع مبالغ، مشتری و پیام منتقل‌شده و تعداد
فایل‌های بررسی‌شده است. IDs، slug، قیمت، موجودی، نام تاریخی و آدرس سفارش باید
تطبیق داده شوند. فایل پس از PUT دوباره GET و SHA-256 آن مقایسه می‌شود. نگاشت
فقط پس از موفقیت ثبت می‌شود. اجرای دوباره امن است؛ دادهٔ منبع و Base64ها حذف
نمی‌شوند. پس از شروع نوشتن در مدل جدید، سند قدیمی صرفاً سابقهٔ زمان انتقال است.

فایل‌های static موجود در `public/` همچنان در خروجی فرانت منتشر می‌شوند؛ انتقال
Base64 مربوط به `store_media` و `customer_media` است. URL خارجی قدیمی بازنویسی یا
حذف نمی‌شود. فایل جدید فقط در Object Storage ذخیره می‌شود. `/api/media/:id`
تصویر عمومی را بدون ورود ارائه می‌دهد؛ `/api/customer/media/:id` مالک یا مدیر
را کنترل می‌کند. bucket را عمومی نکنید: هر دو prefix عمومی و خصوصی در آن وجود
دارند و کنترل دسترسی HTTP بر عهدهٔ API است.

## استقرار داخل ایران

یک Linux VM معمولی با PostgreSQL مدیریت‌شده یا محلی و S3-compatible داخلی کافی
است. API و worker دو فرایند از یک نسخهٔ برنامه‌اند. نیازی به Redis یا Kubernetes
نیست. build را برای سیستم‌عامل میزبان انجام دهید؛ `node_modules` ویندوز را منتقل
نکنید. وابستگی‌ها را پیش از release با lockfile دریافت کنید تا runtime به
دریافت بسته از خارج کشور وابسته نباشد.

1. دیتابیس UTF8، bucket خصوصی، backup خارج از همان دیسک و نقش‌های جداگانهٔ
   migration/runtime ایجاد کنید. برنامه را با superuser اجرا نکنید.
2. نقش runtime به جدول‌های API و sequenceهای مربوطه مجوز CRUD لازم دارد؛ به
   `store_management` هیچ مجوز نوشتن ندهید. جدول‌های قدیمی customer/login/media
   RLS دارند: برای نقش اختصاصی API policy با `USING (true) WITH CHECK (true)`
   روی همان جدول‌ها تعریف کنید؛ نمونهٔ قابل تکرار در
   `ops/database-runtime-grants.sql` روی PostgreSQL ایزوله آزمایش شده است.
   نقش مرورگر/anon نباید این نقش را به ارث ببرد.
   دسترسی مالکیت مشتری در API بررسی می‌شود. نقش migration مالک schema بماند.
3. تنظیمات نمونه، secrets تصادفی، `TRUSTED_PROXY_IPS` دقیق و origin نهایی را
   وارد کنید. PostgreSQL و Object Storage روی اینترنت عمومی باز نباشند.
4. پس از rehearsal و تأیید جداگانهٔ مالک، backup نهایی و توقف نوشتن، migration،
   copy فایل‌ها و import مقاله را روی محیط مقصد اجرا کنید؛ خروجی تطبیق را نگه دارید.
5. `METADATA_API_URL` را به API مهاجرت‌یافته و `VITE_SITE_URL` را به دامنهٔ واقعی
   تنظیم و با `SEO_REQUIRE_COMPLETE=1` build بگیرید. نمونهٔ محلی این مخزن دامنهٔ
   واقعی فروشگاه را تعیین نمی‌کند.
6. staticها را از `artifacts/varsa-shop/dist/public` و `/api` را پشت reverse proxy
   همان دامنه ارائه کنید. نمونه‌های Nginx و systemd در `ops/` هستند؛ مسیر، کاربر
   و TLS باید با میزبان تطبیق داده شوند. API و worker را با یک release راه بیندازید.
7. health/readiness، سفارش دستی، لغو، فایل خصوصی، مقاله و فرم تماس را در staging
   و سپس روی مقصد بررسی کنید. SMS واقعی تنها پس از تنظیم سرویس و opt-in فعال شود.

`GET /api/healthz` زنده‌بودن HTTP را نشان می‌دهد. `GET /api/readyz` وجود دادهٔ
مهاجرت‌یافته، اتصال PostgreSQL و bucket را بررسی می‌کند. readiness ناموفق باید
ترافیک جدید را از نمونه خارج کند. SIGTERM API تا ۱۵ ثانیه برای درخواست‌های جاری
صبر و pool را می‌بندد. worker پس از کار جاری خارج می‌شود؛ پایان اجباری آن با lease
قابل بازیابی است. سقف pool پیش‌فرض برای هر فرایند ۱۰ است: مجموع تمام APIها،
workerها و ظرفیت رزرو مدیریت باید زیر سقف اتصال PostgreSQL باشد.

## worker، خطا و نگهداری

اعلان پیامکی در همان تراکنش تغییر کسب‌وکار به outbox اضافه می‌شود. درخواست HTTP
پیامک notification ارسال نمی‌کند. OTP ورود به‌دلیل عمر کوتاه و جلوگیری از نگهداری
کد خام در صف همچنان مستقیماً به adapter پیامک ارسال می‌شود. adapter فعلی HTTPS
با `{phone,message,purpose,code?,eventId?}` است؛ اتصال ارائه‌دهندهٔ واقعی در محیط
عملیاتی باید با همین قرارداد یا adapter اختصاصی تنظیم شود.

worker با `SKIP LOCKED` کار می‌گیرد، lease شصت‌ثانیه‌ای و حداکثر شش تلاش دارد.
خطاها با backoff نمایی تا یک ساعت برنامه‌ریزی می‌شوند. lease منقضی بازیابی و
تأیید worker قدیمی با token رد می‌شود. درخواست خارجی شناسهٔ پایدار
`varsa-notification-<id>` می‌گیرد؛ بدون پشتیبانی ارائه‌دهنده از idempotency،
ارسال خارجی دقیقاً یک‌باره تضمین نمی‌شود. retry پنل فقط کارهای نهایی failed را
دوباره فعال می‌کند و lease فعال را نمی‌گیرد. رویدادهای `order.created` و
`order.status` فعلاً سوابق پایدارند و integration خارجی برایشان فعال نشده است.

worker رزرو سفارش pending را پس از TTL منقضی و موجودی را یک‌بار آزاد می‌کند.
پیش‌فرض ۲۴ ساعت و بازهٔ مجاز ۶۰ ثانیه تا ۳۰ روز است. تأیید دستی سفارش، انقضای
خودکار را متوقف می‌کند؛ ارسال، رزرو را committed می‌کند. پرداخت همچنان unpaid
است. لغو پیش از ارسال موجودی را برمی‌گرداند؛ مصرف کد تخفیف پس از لغو حفظ می‌شود
که با رفتار قبلی سازگار است. مرجوعی خودکار refund یا restock نمی‌کند.

برای مشاهدهٔ backlog بدون محتوای حساس:

```sql
SELECT status, count(*), min(created_at) FROM outbox GROUP BY status;
SELECT id, attempts, last_error FROM outbox WHERE status='failed';
```

ثبت log ساختاریافته است؛ body، OTP، cookie، token و پارامتر خطای SQL ثبت نمی‌شود.
worker هر ساعت session، OTP و rate limit منقضی را پاک می‌کند. سفارش، فایل و سوابق
outbox خودکار حذف نمی‌شوند؛ retention این داده‌ها باید با سیاست مالک تعیین شود.

## backup، restore و بازگشت

قبل از cutover یک `pg_dump -Fc` با نقش backup و snapshot/copy جداگانهٔ bucket بگیرید.
راز اتصال را در shell history نگذارید؛ از secret file/PGPASSFILE با دسترسی محدود
استفاده کنید. نمونهٔ فرمان با اتصال از محیط امن:

```sh
pg_dump --format=custom --file=varsa-before-cutover.dump
createdb varsa_restore_check
pg_restore --exit-on-error --no-owner --dbname=varsa_restore_check varsa-before-cutover.dump
```

restore را روی دیتابیس **جدید و ایزوله** انجام دهید و تعداد سفارش‌ها، جمع total،
شناسه‌ها، snapshotها و هش فایل‌های نمونه را بررسی کنید. آزمون خودکار این تغییر
مهاجرت را بررسی می‌کند؛ اجرای backup/restore روی سرویس واقعی میزبان هنوز مرحلهٔ
فعال‌سازی عملیاتی است. برنامهٔ backup منظم، retention، رمزگذاری و یک کپی روی
میزبان مستقل را پیش از راه‌اندازی واقعی تنظیم کنید.

پیش از پذیرش نوشتن جدید، rollback با app قدیمی و backup قدیمی انجام می‌شود.
پس از پذیرش سفارش جدید، بازگردانی سادهٔ backup باعث ازدست‌رفتن سفارش خواهد شد:
ابتدا نوشتن را متوقف، سفارش‌ها و فایل‌های جدید را export و با مدل قدیمی reconcile
کنید یا مشکل را در نسخهٔ جدید اصلاح کنید. هیچ down migration مخربی ارائه نشده است.
نسخهٔ فعلی برای انتشار خودکار یا تغییر محیط عملیاتی مجوز ندارد.
